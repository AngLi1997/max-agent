# 重置密码功能设计

## 背景

当前系统已经具备以下能力：

- 基于 RBAC 的权限控制
- 用户创建时生成临时密码，并将 `must_change_password` 设为 `true`
- 登录后通过 `/auth/me` 返回 `mustChangePassword`
- 前端通过 `ForcePasswordChangeModal.vue` 强制用户首次登录后修改密码
- 登录态基于 Redis token

本次需求是在现有机制上新增“管理员重置密码”能力，而不是重新设计另一套密码生命周期。

## 目标

1. 新增“重置密码”权限，并默认分配给超级管理员角色
2. 在用户管理页面提供“重置密码”操作
3. 管理员确认后，系统随机生成临时密码并展示给管理员
4. 被重置用户的当前登录态立即失效
5. 被重置用户下次登录后必须修改密码
6. 只要拥有 `user:reset-password` 权限，就可以重置任意用户密码

## 非目标

1. 不新增单独的“重置原因”字段
2. 不支持管理员手动输入新密码
3. 不新增独立的“密码状态”页面或列表字段
4. 不在前端额外实现“你已被管理员重置密码”的专门提示

## 方案选择

采用方案 1：新增独立权限 + 新增重置密码接口 + 复用现有强制改密机制。

原因：

- 与现有 RBAC 体系一致
- 与“创建用户 -> 临时密码 -> 强制改密”的现有链路一致
- 权限边界清晰
- 后续可以灵活把该权限分配给任意角色，而不需要改代码结构

## 后端设计

### 权限点

新增权限点：`user:reset-password`

- 类型：按钮
- 名称：`用户重置密码`
- 默认通过 `backend/app/db/seed.py` 写入权限种子数据
- 超级管理员角色继续沿用当前逻辑，自动获得全部权限，因此会自动拥有该权限

### 接口设计

新增接口：`POST /users/{user_id}/reset-password`

权限要求：`require_permission("user:reset-password")`

成功响应：

```json
{
  "message": "密码重置成功",
  "temporaryPassword": "随机生成的临时密码"
}
```

错误响应语义：

- `404`：目标用户不存在
- `403`：当前用户没有 `user:reset-password` 权限

### 业务规则

接口执行流程：

1. 根据 `user_id` 查询目标用户
2. 若目标用户不存在，返回 `404`
3. 生成随机临时密码，继续复用现有随机密码生成逻辑
4. 将目标用户密码更新为新临时密码的哈希值
5. 将目标用户 `must_change_password` 设为 `true`
6. 立即失效目标用户当前所有 token
7. 写入操作日志，记录“重置用户密码”
8. 返回临时密码给前端展示

### token 立即失效设计

当前系统基于 Redis token，但只有“按 token 删除”的能力，没有“按用户删除全部 token”的能力。

为满足“重置后当前登录态立即失效”，在现有 `SlidingRedisStrategy` 上补充“用户 token 索引”机制。

#### Redis 键设计

- token 主键：沿用现有 `max_agent_token:<token>`
- 用户 token 集合：新增 `max_agent_user_tokens:<user_id>`

#### 写入策略

用户登录成功时：

1. 按现有方式写入 `max_agent_token:<token>`
2. 将该 token 追加到 `max_agent_user_tokens:<user_id>` 集合
3. 为 `max_agent_user_tokens:<user_id>` 设置过期时间，和 access token 生命周期保持一致

#### 退出策略

用户主动退出时：

1. 删除当前 token 对应的 `max_agent_token:<token>`
2. 从 `max_agent_user_tokens:<user_id>` 集合中移除该 token
3. 重新刷新 `max_agent_user_tokens:<user_id>` 的过期时间，避免集合长期残留

#### 重置密码策略

管理员重置用户密码时：

1. 读取 `max_agent_user_tokens:<user_id>` 集合中的全部 token
2. 批量删除对应的 `max_agent_token:<token>`
3. 删除 `max_agent_user_tokens:<user_id>` 集合

批量删除时允许集合中存在已自然过期的旧 token 条目；即使对应的 token 主键不存在，也不影响重置成功。

结果：被重置用户所有浏览器和设备上的现有登录态都会在后续请求时失效，并收到 `401`。

### 代码边界

- 路由层负责参数、鉴权依赖、HTTP 错误映射、返回结构
- 用户服务层负责：生成临时密码、更新密码、设置 `must_change_password`
- 认证服务层负责：维护用户 token 索引、批量失效指定用户所有 token
- 审计服务负责记录操作日志

这样可以保持“用户管理”和“认证令牌管理”职责分离。

## 前端设计

### 用户管理页交互

位置：`frontend/src/views/setting/user/index.vue`

在操作列下拉菜单中新增“重置密码”项。

显示条件：当前用户拥有 `user:reset-password` 权限。

点击后的交互流程：

1. 先弹出确认框
2. 用户确认后调用 `POST /users/{id}/reset-password`
3. 接口成功后弹出结果框，展示新临时密码
4. 关闭结果框后调用一次 `fetchData()`，保持与编辑、删除后的交互一致

### 确认框文案

- 标题：`确认重置密码`
- 内容：`确定要重置用户「xxx」的密码吗？重置后该用户当前登录态将立即失效。`
- 按钮：`取消` / `重置`

### 结果框文案

- 标题：`密码重置成功`
- 内容：显示新临时密码
- 补充提示：`请妥善保存，该用户下次登录后需要立即修改密码。`

### 前端权限处理

前端只根据 `user:reset-password` 控制“重置密码”菜单项是否显示，不对目标用户是否为内置用户做额外限制，也不单独隐藏按钮。

原因：

- 当前规则已经简化为“只要拥有该权限，就可以重置任意用户密码”
- 前端只负责展示权限结果，不复制更多业务分支
- 后端仍然作为最终权限裁决点，保证行为一致

如果后端返回 `403`，前端按现有统一错误提示方式展示后端文案即可。

## 强制修改密码链路

本次功能不新增新的改密流程，直接复用现有机制：

1. 管理员重置密码后，目标用户 `must_change_password = true`
2. 该用户重新登录成功后，请求 `/auth/me`
3. 后端返回 `mustChangePassword: true`
4. 前端 `userStore` 更新状态
5. `App.vue` 中的 `ForcePasswordChangeModal.vue` 自动弹出
6. 用户必须修改密码后才能继续使用系统

这样能保证“创建用户”和“管理员重置密码”两条入口最终都汇聚到同一个强制改密流程。

## 异常处理

### 后端

- 用户不存在：返回 `404`
- 权限不足：返回 `403`

本次不引入额外复杂状态校验，避免增加与需求无关的分支。

### 前端

- 重置失败时，展示后端返回的错误文案
- 被重置用户若此时在线，不额外显示专门提示
- 该用户后续任一请求触发 `401` 时，复用现有 axios 拦截器自动清理登录态并跳转登录页

## 测试与验证

### 后端测试

至少覆盖以下场景：

1. 重置密码成功后返回临时密码
2. 重置密码成功后目标用户 `must_change_password = true`
3. 重置后旧密码失效
4. 重置后新临时密码可正常登录
5. 重置后目标用户已有 token 全部失效
6. 有权限的角色可以重置任意用户
7. 无权限用户调用接口返回 `403`

### 前端验证

至少验证以下场景：

1. 有权限时用户管理操作菜单显示“重置密码”
2. 确认重置后能弹出新临时密码
3. 重置成功后列表可正常刷新
4. 被重置用户重新登录后会被强制要求修改密码
5. 被重置用户若原本在线，在下一次请求时会被 `401` 拦回登录页

## 影响范围

### 后端

- `backend/app/db/seed.py`
- `backend/app/api/routes/users.py`
- `backend/app/services/system_users.py`
- `backend/app/services/auth.py`
- 可能新增或调整相关 schema
- 相关后端测试文件

### 前端

- `frontend/src/api/user.ts`
- `frontend/src/views/setting/user/index.vue`
- 可能不需要改动 `ForcePasswordChangeModal.vue`，因为直接复用现有流程

## 实施原则

1. 不新增与需求无关的抽象
2. 不重做现有强制改密流程
3. 将“按用户批量失效 token”能力收敛在认证服务层
4. 将“是否允许重置目标用户”作为后端最终裁决
5. 前端尽量只负责触发动作和展示结果，不复制复杂权限规则
